# FL-102 · Código incorrecto, vencido o con demasiados intentos

> Caso de QA escrito antes de construir (WP-53, ola 3, etapa A1). WP-42 lo actualiza con lo que cambie al construir. Fuente: `docs/flows-catalog.md` FL-102; diseño en ADR-0015 §1.1 y §3.2; copy en `docs/landing-spec.md` §8.3 y §8.8.

| Campo | Valor |
|---|---|
| Área | L · Alta pública, cuenta de invitado y leads |
| Actores · canal | Visitante · web (`/signup/verify`) |
| Reglas | Tope de códigos errados por alta y de confirmaciones por hora por IP (`guest-limits.ts`, ADR-0015 §3.2); toda respuesta que no es `CONFIRMED` sale a los 1.500 ms del inicio del pedido (ADR-0015 §1.1); la pantalla no distingue errado de vencido |
| Depende del modelo | No |
| Pruebas | U `routers/signup.test.ts`, `signup/rate-limits.test.ts`, `routers/signup-timing.test.ts` · LF `signup.flow.test.ts` · UI `auth.spec.ts` · SR `SC-26/4` |

## Entrada

- Un alta en rama `NEW` con el código ya enviado (pasos 1 a 5 de FL-101), con el buzón sintético `qa-signup-<runId>-a@sim.legajo.demo.craftech.io`.
- Reloj real inyectado (`U`, `LF`) para vencer el código y el `SIGNUP#` (24 h).
- `CloudFront-Viewer-Address` de prueba con una IP de documentación (RFC 5737) para el tope por IP.
- `U`: altas en las ramas `SUPPRESSED`, `INELIGIBLE` y `FAILED`.
- Topes: `packages/shared/src/guest-limits.ts` (5 errores por alta y 30 confirmaciones por hora por IP hoy; los tests los importan).

## Pasos

1. Cargar un código errado.
2. Seguir errando hasta superar el tope de errores.
3. Con el alta cerrada, cargar el código correcto.
4. En otra alta: avanzar el reloj inyectado 24 h y cargar el código; en otra, dejar vencer el `SIGNUP#`.
5. Desde la misma IP, superar el tope de confirmaciones por hora.
6. `signup.confirm` sobre altas en `SUPPRESSED`, `INELIGIBLE` y `FAILED`.
7. `SR` `SC-26/4`: un código errado en el alta del buzón `a`.

## Resultado esperado

1. Código errado → `CODE_INVALID {attemptsLeft}`; la pantalla muestra `verify.errors.invalid` ("El código no es válido o venció…") y, con `attemptsLeft` ≤ 2, suma `verify.errors.attemptsLeft(n)` con el número de la respuesta (nunca escrito a mano).
2. El error que alcanza el tope → `EXPIRED`; desde ahí también el código correcto da `EXPIRED`; la pantalla muestra `verify.errors.expired` con "Empezar de nuevo", que vuelve a `/signup` con los datos y sin la contraseña.
3. Código vencido o `SIGNUP#` vencido → `EXPIRED`.
4. Confirmaciones por encima del tope por IP → `RATE_LIMITED {retryAfterSec}` y el estado `rateLimited` con `ceil(retryAfterSec / 60)` minutos.
5. `SUPPRESSED`, `INELIGIBLE` y `FAILED` → `CODE_INVALID` sin ninguna llamada a Cognito.
6. Toda respuesta que no es `CONFIRMED` sale a los 1.500 ms del inicio del pedido, con o sin llamada a Cognito.
7. Ningún lead ni grupo; el usuario sigue `UNCONFIRMED` hasta que `GUEST_SWEEP` lo borra (FL-122); el contador de intentos vive en `SIGNUP#`.
8. (`SC-26/4`) `CODE_INVALID {attemptsLeft: 4}` y ningún lead para `a` antes de `SC-26/5`.

## Cobertura por nivel

| Nivel | Prueba | Qué asierta con la etiqueta `[FL-102]` |
|---|---|---|
| U | `routers/signup.test.ts` | `CODE_INVALID {attemptsLeft}` por cada error; `EXPIRED` al llegar al tope y con el código correcto después; `EXPIRED` por vencimiento; ramas `SUPPRESSED`, `INELIGIBLE` y `FAILED` → `CODE_INVALID` sin Cognito |
| U | `signup/rate-limits.test.ts` | Contador `Runtime/RL#…` de confirmaciones por IP agregada: el primero por encima del tope en la ventana → `RATE_LIMITED {retryAfterSec}`; `expiresAt` = fin de la ventana + 1 h |
| U | `routers/signup-timing.test.ts` | Toda respuesta de `signup.confirm` que no es `CONFIRMED` sale a los 1.500 ms en todas las ramas |
| LF | `signup.flow.test.ts` | Alta → errores hasta el tope → `EXPIRED` → alta nueva desde `/signup` |
| UI | `auth.spec.ts` | Código errado hasta el tope: mensajes, intentos restantes, "Empezar de nuevo"; `RATE_LIMITED` con el doble configurado |
| SR | `SC-26/4` | Un código errado → `CODE_INVALID {attemptsLeft: 4}` |

## Oráculo

No aplica: flujo determinista.

## Evidencia

- Vitest filtrado por `[FL-102]`; reporte de `auth.spec.ts` con las capturas del error y de `EXPIRED`.
- `scenario-report.json` (`SC-26/4`): respuesta (`status` y `attemptsLeft`) y duración del pedido.
- Nunca se guardan códigos de verificación, emails de leads, contraseñas ni tokens.
